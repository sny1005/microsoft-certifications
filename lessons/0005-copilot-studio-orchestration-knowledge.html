1. (Lesson 1) When is Copilot Studio the right rung of the ladder — and what constraints come with it?

Reveal

When you need a purpose-built agent — business process automation, publishing to Teams/web/D365 channels, autonomous triggers, agent flows — but still want a governed, low-code, fast loop that business users can co-own. Constraints: connector-scoped data, platform-enforced guardrails, medium risk tier.

2. (Lesson 2) Two reps ask the same agent the same question. One gets a precise, cited answer; the other is told no such content exists. Which grounding dimension failed, and why is it silent?

Reveal

Availability. Retrieval is permission-trimmed per user at query time, so the second rep's agent answers from a poorer evidence base and nobody gets an error. The fix lives at the permission layer, and you detect it by testing retrieval as personas, not as admin.

3. (Lesson 4) Write the ROI% formula, and state exactly where the adoption factor enters the annual-benefit arithmetic.

Reveal

ROI% = (Net_Benefit / Annual_TCO) × 100, where Net_Benefit = Annual_Benefit − Annual_TCO. Adoption multiplies the volume term (runs per year), not the minutes saved — skip it and you overstate the benefit.

Agent anatomy: the six components

Every Copilot Studio agent — task, autonomous, or prompt-driven — is assembled from the same six components. Learn each as what it is → a concrete example; the exam describes a requirement and asks which component owns it. [source]

ComponentWhat it isConcrete example
GoalsThe agent's mission — outcome-based, actionable, observable, testable"Resolve order-status questions without a human"
SkillsLanguage understanding, data interpretation, planning, executionParse a refund request; plan the lookup steps
ActionsConnectors, custom connectors, APIs, Dataverse operations, cloud flows — each needs input parameters, an output schema, auth, and error handlingA GetOrderStatus connector; a CreateCase Dataverse action
KnowledgeSharePoint, manuals, SOPs, Dataverse, knowledge bases — must be accurate, recent, governed, indexedThe returns-policy SharePoint site plus product-manual PDFs
ContextThe conversation state the agent carries through the dialogThe order number captured two turns ago, reused by the next action
Safety & RulesHard behavioral constraints the agent must never cross"Never override credit limit"; "ask before submitting order"; "escalate on complaint keywords"

The Foundry analogy: actions are tool schemas (inputs, outputs, auth, error handling) wearing a low-code wrapper, and Safety & Rules are system-message guardrails the platform enforces rather than the prompt politely requesting. Design best practices: start with one high-value workflow; keep goals small and focused; ground on clean structured data; scope actions least-privilege; add monitoring and logging; test edge cases. [source]

The three agent types — and when each

TypeStarts whenBuilt fromChoose when
Task agentThe user asksThe six anatomy components; topic-driven dialogs with question nodes and actionsGuided, user-initiated workflows with structured steps — reset MFA, create a ticket, check an order
Autonomous agentAn event fires: user input, system changes, or schedulesGoals, triggers, instructions (business rules such as VIP escalation), knowledge sources, actions (APIs, records, emails, CRM updates)Work that should start itself — a Dataverse row is created, a schedule fires — without waiting for a prompt
Prompt-driven agentThe user asks, but no authored topic is neededGenerative mechanisms: the Generative Answers node, system topics, condition nodes, event triggersOpen-ended Q&A over knowledge, where answers are generated from sources rather than authored as topics

Three details carry exam weight. First, the prompt-driven agent's toolbox: the Generative Answers (NLU Boost) node answers from knowledge when no topic matches — usable as fallback — and its responses can be stored in variables, rendered in Adaptive Cards, and custom-formatted; condition nodes branch on variables with AND/OR and if/elseif/else logic, with Power Fx formulas for advanced cases; system topics trigger automatically. Second, event triggers: they act without a user prompt (file uploaded, task completed, Dataverse row added, schedule), their payloads carry data, instructions, and context, they must be explicitly authorized, and they impact billing — an unauthorized or unbudgeted trigger is a governance defect, not a convenience. Third, the autonomous-agent build loop: identify a simple high-value use case → build (goal, instructions, knowledge, triggers, actions via Power Automate/connectors/Dataverse) → test accuracy, grounding, and action execution repeatedly → deploy to Teams → monitor and refine. [source, source, event triggers]

Classic vs generative orchestration — the exam's favorite fork

Orchestration is the agent's control flow: given a user turn, decide what runs. Copilot Studio offers two modes, and the Design domain tests the difference relentlessly. [source]

DimensionClassic orchestrationGenerative orchestration
How a topic is selectedTrigger-phrase matchTopics, agents, and tools selected by their descriptions
Where tools can runOnly from within a topicWherever the plan calls for them
Position of knowledgeSearched only as a fallbackProactive knowledge search, first-class in the plan
Scope per turnA single topic runsCombines topics + tools + knowledge in one turn
Missing inputsYou author question nodes for every slotAuto-generates questions for missing inputs
ResponsesYou author message nodesAuto-generates responses

Two generative-mode facts to memorize. Enabling generative orchestration auto-creates the "Conversational boosting" system topic — the mechanism that serves dynamic answers from knowledge when no topic matches. And generative answers search up to 25 knowledge sources with GPT-based relevance filtering; you can optionally enable general knowledge so the agent can answer out-of-domain questions from the model's own knowledge — a choice you should make deliberately, not by default. [source, source]

The Foundry analogy that makes this stick. Classic orchestration is an explicit intent router: trigger phrases are the route table, each topic is a request handler, and nothing executes unless a route matches. Generative orchestration is Foundry Agent Service's automatic tool calling: you describe the topics, tools, and knowledge, and the model plans which to invoke — filling missing parameters by asking the user, exactly as function calling asks for missing arguments. If you would solve it with an explicit dispatcher in code, that's classic; if you would hand the model a tool list and let it plan, that's generative. The judgment the exam wants: unpredictable, free-form requests that blend answers with actions → generative; a fixed set of commands where routing must be exact and auditable → classic discipline (see the NLU section below).

Knowledge architecture

Knowledge is where Copilot Studio agents get their grounding — and where the Design domain plants its limits-and-tradeoffs questions. [source]

Where knowledge attaches — three levels

Knowledge can be applied at the agent level (available everywhere), at the topic level (scoped to one conversation flow), or on a generative answers node (scoped to that exact step). The priority rule: node-level sources are prioritized over agent-level sources. That is how you stop a general-purpose agent from answering a specialized flow's questions from the wrong corpus — override at the node, don't restructure the agent. [source, source]

Source types

SourceKindNotes
Public websitesUnstructuredPublic pages only — no auth, no private content
Uploaded documentsUnstructuredPDF/Word/PPTX indexed into Dataverse
SharePointUnstructuredPermission-trimmed per user at query time
DataverseStructuredTables and rows — records, not documents
Enterprise connectors via Microsoft SearchVariesOneDrive, Salesforce, ServiceNow, and more
Azure OpenAI "on your data"Your own indexBring an existing retrieval index to the generative answers node

How unstructured data is processed

This is lesson 2's RAG pipeline delivered as SaaS. Unstructured content is ingested into Dataverse, chunked, and vectorized; a background sync keeps it fresh; and at query time, retrieval runs per-user permission checks before anything reaches the model. Every consequence from lesson 2 follows: grounding is per-user, over-permissioned content is a grounding bug fixed at the permission layer, and availability failures are silent — you test as personas. The difference from Foundry RAG is that Dataverse is the index substrate and the platform owns the pipeline; you trade control for zero ops. [source]

The two hard limits — memorize both numbers

  1. 500 knowledge objects per agent. The total ceiling on knowledge items attached to one agent.
  2. Max 5 unstructured sources in simultaneous retrieval. Attach eight SharePoint sites and uploaded manuals if you like — any single retrieval searches at most five of them. The design consequence: consolidate unstructured content into fewer, well-curated sources, or front a large corpus with Azure AI Search instead of attaching it piecemeal.

Azure AI Search as a knowledge source

For volume and relevance beyond what the built-in pipeline offers, point the agent at Azure AI Search: vector indexes with semantic ranking, authenticated by key, certificate, or Microsoft Entra ID, with metadata-based citation mapping so answers cite the right document. It is the preferred source for large content volume and enterprise-grade relevance — the same service you already know from Foundry work, consumed here as a knowledge source rather than wired through an SDK. [source]

Topics: the unit of conversational logic

A topic binds conversational logic to an intent. Its components: trigger phrases (written in real user language, not system-speak), message nodes (what the agent says), question nodes (choice lists, text, dates, numbers — the slots you fill), conditions and branching, and actions (Dataverse updates, Power Automate, external data). Topics get selected by trigger phrases, NL matching, or — under generative orchestration — by description. [source, source]

The five topic types

TypePurposeExample
InstructionalWalk the user through a how-to"Reset MFA method"
ActionDo something in a system"Create support ticket"
InformationalAnswer a stable fact"Business hours"
SystemPlatform-owned conversation momentsGreeting, escalation, fallback
ReusableShared logic called from many topicsAuthentication

Entity extraction is what makes question nodes useful: the node pulls structured values — names, numbers, dates — out of the user's reply so downstream actions receive clean parameters instead of raw prose. Design best practices: clarity and brevity; structured questions; entity extraction for the values actions need; consistent tone (Microsoft Writing Style Guide); and test with real user phrasing, not the phrasing the team invented in the design doc. [source]

System topics — including the one people forget

System topics trigger automatically at platform-owned moments: greeting, escalation, fallback, end of conversation, multiple-topics-matched disambiguation, and error handling. The disambiguation one earns its keep: when a user turn matches more than one topic, the agent asks the user which they meant — a choice list instead of a coin flip. [source]

The fallback topic pattern

When no intent matches, the fallback topic owns the turn. The pattern: acknowledge the miss ("I'm not sure I understood that") → offer alternatives the agent can actually do → optionally redirect to a human → capture feedback so coverage improves. The discipline that goes with it: don't overuse fallback — build strong intent coverage first. A fallback that fires constantly is a coverage metric telling you to author more topics, not a feature to be proud of. Analogy for the Foundry-minded: topics are intent-routed handlers, and fallback is the 404 handler — you need one, but a busy 404 means your routes are wrong. [source]

NLU vs CLU vs generative — the language-understanding decision

Three mechanisms can interpret what the user said. They are not interchangeable, and the exam's job is to make you prove you know when each wins. [source]

The best practices that close the section: start with NLU/CLU for structured tasks — don't pay generative prices for deterministic work; always ground generative answers — ungrounded generation is a hallucination with a UI; wrap generative behavior in guardrails (instructions, actions, topic triggers); and weigh the cost and compute of generative before defaulting to it. [source]

Reasoning modes: standard vs deep

Independent of orchestration mode, an agent's behavior (instructions, knowledge, actions, policies) runs on one of two reasoning modes: [source, source]

Standard reasoningDeep reasoning (preview)
Built forConversational responses, summaries, simple calculations, basic workflow helpMulti-step tasks, complex business rules, analytical processes, decision trees, scenario planning, constraint/trade-off evaluation
ProfileFast, low compute, high-volumeSlower and costlier per call
Choose whenThe default; volume workloadsHigh-precision logic, multi-stage evaluation, historical-data recommendations, validation logic, problem decomposition

The judgment: deep reasoning's extra latency and cost are justified only when the task genuinely decomposes into dependent steps under constraints — a decision tree with trade-offs, a multi-stage validation. For the everyday volume of lookups and summaries, standard reasoning is the correct answer and deep reasoning is an expensive distractor. This is lesson 4's economics applied per call: match the reasoning tier to the task, the same way the model router matches the model to the request.

Prompt actions: reusable instruction blocks

A prompt action is a reusable block of instructions an agent calls to generate responses, reason, transform or summarize, follow structured instructions, and interact with variables. Think of it as a pure function with a prompt body: defined once, called from many places, versioned and governed. [source]

Prompt Coach — the five sections

Copilot Studio's Prompt Coach template enforces a consistent structure: Goal | Context | Instructions/Rules | Examples (optional) | Output Format. The authoring principles that go with it: task clarity (imperative verbs); organizational tone (Microsoft Writing Style — clear, concise, action-oriented); output control (word limits, required fields, explicit exclusions). [source]

The five types — and where they embed

TypeWhat it does
TransformReshape content from one form to another
SummarizeCondense content — e.g., summarize a case before escalation
ExtractPull specific values out of content
GenerateCreate new content
ClassifyAssign content to a category

Prompt actions embed in four places: topics, agent flows (reasoning before an action fires), fallback logic, and business processes. The governing best practice is modular — one task per prompt: a summarize-and-classify prompt does two jobs badly and can't be reused for either. Use constraints, examples sparingly, guarded language; test with multiple phrasings; run Prompt Coach; and document each prompt action for governance and auditing — these are the artifacts lesson 3's CoE prompt library exists to curate. [source]

Agent flows vs Power Automate cloud flows

Agent flows are automation native to Copilot Studio: a trigger (manual, scheduled, system event, or another agent) plus actions, with consistent execution and end-to-end visibility. Two facts make them architecturally distinct: no Power Automate license is required, and usage is billed from Copilot message capacity. You author one by describing it in natural language — Copilot generates the flow — or by using the visual node-based designer, and they integrate with Forms, D365, Dataverse, email, APIs, and custom connectors. [source, source]

Agent flowPower Automate cloud flow
LicensingNo Power Automate license; billed from Copilot message capacityRequires a Power Automate license
Best forAI-driven conversational automationEnterprise integration
Builder experienceNatural-language authoring plus visual designer, inside Copilot StudioThe Power Automate design surface

The durable-functions analogy: an agent flow is a durable function wearing a natural-language frontend — a trigger, then deterministic, observable step execution with state carried for you. Reach for a cloud flow when the automation is really enterprise integration that happens to exist near an agent. Best practices: one clear scenario per flow; concise instructions; prototype in natural language, then refine visually; test the agent and the flow together; monitor the analytics; and keep flows modular — one per major task, the same discipline as prompt actions. [source]

Check yourself

1. Customers write in unpredictable, free-form language, and a single reply often needs both a policy answer and a refund action. Topics exist for the top intents. Which orchestration mode should the agent use?

Generative orchestration exists for exactly this: unpredictable phrasing, and a turn that combines topics, tools, and knowledge in one plan — with proactive knowledge search rather than knowledge-as-fallback. Option d contradicts itself: combining beyond a single topic is the defining capability.

2. A support agent has eight unstructured sources — SharePoint sites and uploaded manuals — attached at the agent level. Answers draw on five sources but never the other three, for every test user. Most likely cause?

The simultaneous-retrieval ceiling is five unstructured sources — the other three are simply never searched. "Every test user" rules out permission trimming, which is per-user; and 500 objects is a total-attachment ceiling, not a per-retrieval one. The fix: consolidate sources or front the corpus with Azure AI Search.

3. Inside one topic, a generative answers node names the HR policy library as its source. The agent also has agent-level knowledge across the public website. When the conversation reaches that node, what does it search?

Node-level sources are prioritized over agent-level sources. That priority is the designed mechanism for scoping a specialized flow to its own corpus without restructuring the whole agent's knowledge.

4. Users regularly ask things no topic covers. You want the miss acknowledged, a few alternative requests offered, an optional handoff to a human, and the miss logged for review. What do you configure?

Acknowledge → alternatives → optional human redirect → capture feedback is the fallback topic pattern. The multiple-topics-matched topic is disambiguation — it fires when several topics match, not when none do. And if fallback fires often, invest in intent coverage rather than decorating the fallback.

5. A bank's agent must run an account-closure process: a fixed set of commands, deterministic and auditable responses, regulated wording. Which language approach fits best?

Structured commands plus a regulated process needing deterministic responses is standard NLU's explicit niche — the decision table maps both rows there. CLU handles varied phrasing you don't have; generative adds cost and nondeterminism you can't accept; deep reasoning solves a different problem.

6. An HR agent must recognize widely varied phrasings across a bounded set of benefits intents, pull dates and names out of requests, and work in three languages. Best fit?

Varied phrasing within bounded topics, entity extraction, and multilingual support are CLU's three named strengths. Standard NLU wants low variability you don't have; trigger-phrase lists don't scale to this; generative answers retrieve knowledge rather than route intents with extracted entities.

7. Makers without Power Automate licenses need an automation the agent can trigger: create a Dataverse record, then email a confirmation. It should be authored in natural language. Which tool?

Agent flows are native to Copilot Studio, need no Power Automate license, bill from Copilot message capacity, and author from natural language — every constraint in the stem. Computer Use is the no-API last resort, and a custom connector is plumbing, not the automation itself.

8. An agent answers a high volume of simple order-status questions — straightforward lookups, brief conversational replies, simple math. Latency and cost matter. Which reasoning mode?

Simple, high-volume, latency-sensitive work is standard reasoning's stated profile. Deep reasoning is for multi-step, constraint-heavy tasks — touching Dataverse doesn't make a lookup one. Option d invents a policy; preview status is a consideration, not the decision criterion named in the scenario.

9. A returns agent must (1) summarize the conversation for the case record and (2) classify the return reason. How should the prompt actions be structured?

Modular, one task per prompt: a Summarize action and a Classify action, each reusable, testable, and governable on its own. A combined prompt does both jobs worse and neither job reusefully; generative answers retrieve knowledge; system topics aren't a vehicle for prompt logic.

10. An autonomous agent should start when a Dataverse row is added and use the row's data. Which statement about its event trigger is correct?

Event-trigger payloads carry data, instructions, and context; triggers must be explicitly authorized; and they impact billing. The whole point of an autonomous trigger is firing without a user session — options a and b each drop one of the two governance facts the exam pairs together.

Apply it: Contoso's customer-service build

Decide each before opening the reveal.

A. Contoso wants a customer-service agent. Requirements: customers write in free form; the top two intents (order status, start a return) are well known and need structured data capture; policy answers live on three SharePoint sites; product manuals are PDFs; case history sits in Dataverse; complaints must reach a human; the agent must create cases. Design the orchestration mode, knowledge architecture, topic set, and safety rules.

Your design?

Orchestration: generative — free-form phrasing, turns that blend knowledge answers with actions, and auto-generated questions for missing inputs; the well-known intents still get authored topics, which generative mode selects by description. Topics: an action topic per top intent ("Check order status", "Start a return") with question nodes and entity extraction (order number, dates); system topics left in place, including multiple-topics-matched disambiguation. Knowledge: the three SharePoint sites (permission-trimmed) plus the uploaded PDF manuals (indexed into Dataverse) — four unstructured sources, inside the five-source retrieval ceiling; case history as a structured Dataverse source. Safety & rules: "escalate on complaint keywords" wired to the escalation system topic. Action: a CreateCase Dataverse action or a modular agent flow. [source, source]

B. Six weeks later, Contoso reports: every user who asks "How many vacation days do I accrue at year five?" gets an answer drawn from the public benefits website instead of the employee policy manual — regardless of who asks. Give an ordered diagnosis.

Your diagnosis?

Work the checklist in order. (1) General knowledge: if enabled, the agent can answer out-of-domain from the model's own knowledge — check it first and disable it if in-domain-only answers are required. (2) The five-source ceiling: count unstructured sources; if the manual's source is the sixth, it is never searched — consolidate, or move the corpus to Azure AI Search. (3) Node-level priority: if a generative answers node in this flow names its own sources, those override agent-level sources — a stale or wrong node-level source answers every turn. (4) Not permission trimming: the failure hits every user identically, and trimming is per-user — "everyone gets the wrong source" is the tell that rules it out before you spend an hour in SharePoint permissions. [source, source]

C. Contoso's equipment-checkout process: an employee requests equipment → eligibility is checked against Dataverse → a manager approves → the asset record is updated → a confirmation email goes out. Separately, employees ask policy questions ("Can I check out a laptop for travel?"). Decompose this into topics, prompt actions, and automation.

Your decomposition?

Policy questions: generative answers over the equipment-policy SharePoint site — informational coverage, no authored topics per question. "Request equipment" action topic: question nodes with entity extraction (equipment type, dates), a condition node branching on the eligibility result. Prompt actions: a Summarize action that condenses the request and conversation for the manager's approval, and a Classify action for the equipment category if free-text entry is allowed — two modular prompts, one task each. Automation: one agent flow per major task — a flow triggered by the agent to create the asset record and route the approval (manual trigger from the topic, or a system-event trigger on the Dataverse row), and the confirmation email as part of that flow's actions; test agent and flow together. If eligibility is declined, the topic branches to a polite refusal with an escalation option rather than forcing the process through. [source, source]
