Designing extensibility across the agent platforms

Custom models, M365 agents, Copilot Studio's four layers, MCP, and Computer Use — how far each platform stretches

Lesson 7 of your AB-100 course, and the second half of the Design domain. Lessons 5–6 went deep inside two platforms — Copilot Studio's internals, the D365 Copilot surface. This lesson maps the boundaries between platforms: extensibility is the question of how far each rung of lesson 1's ladder can stretch before you must drop to the next one down. Every rung has a sanctioned stretch — declarative agents extend M365 Copilot, four layers extend Copilot Studio, MCP extends Dynamics 365 F&O, Computer Use extends anything with a UI — and the Design domain tests whether you pick the stretch that stays highest on the ladder. 1. (Lesson 1) State the SaaS-first principle, and name the condition that justifies climbing from "extend Microsoft 365 Copilot" up to "build in Copilot Studio."

Reveal

Always open by asking whether a prebuilt SaaS agent meets the functional requirements — if yes, stop. 2. (Lesson 5) Knowledge can attach at three levels in Copilot Studio. When node-level and agent-level sources conflict, which wins — and what are the two hard knowledge limits?

Reveal

Node-level sources are prioritized over agent-level sources. The limits: 500 knowledge objects per agent, and at most five unstructured sources in simultaneous retrieval — attach eight SharePoint sites and any single retrieval still searches only five of them.

3. (Lesson 6) A Copilot in Sales plugin must call an external API as the calling seller. What authentication setup is required, and where must the connector be created?

Reveal

OAuth 2.0 with Microsoft Entra ID, two app registrations, and Enable onbehalfOf login = true so the backend receives OBO tokens as the seller. The connector must be built in an environment with Dynamics 365 apps enabled — the default environment is unsupported. Keep this chain in mind: MCP later this lesson is the same idea (a standardized contract), pointed at context instead of actions.

Extensibility means knowing where each rung ends

Lesson 1 gave you the ladder; this lesson gives you the edges. The extend-M365-vs-build-custom decision is the framing every other section hangs on, and Microsoft's comparison matrix is the exam's own vocabulary for it. [source, source]

Extend when: core Copilot already does most of the tasks; the workflows are productivity work inside M365 apps; the need is org knowledge plus simple tasks; you want the built-in Responsible AI guardrails; the custom logic is simple. The extension mechanisms are connectors/plugins, org knowledge sources, and document/communication automation. Build custom when: specialized workflows beyond Copilot; custom reasoning, multi-step logic, or orchestration; direct system APIs, external apps, or operational autonomy; multi-agent collaboration; execution outside M365. Custom agents earn their cost in case management, field-operations automation, industry verticals, and multi-agent ecosystems. Everything below is the detailed "how" of both columns.

Custom models in Foundry: the judgment, not the mechanics

You know Foundry cold, so this section is deliberately compact. AB-100 never asks can you fine-tune — it asks is a custom model justified here, and the justified list reads like a set of exceptions. [source, source]

A custom model is justified by: domain-specific language or reasoning (legal, healthcare, engineering, finance, manufacturing); high-impact decisions (compliance, financial, safety); data sovereignty or governance mandates; unique workflows and personalization beyond what prebuilt copilots offer; and cost optimization of high-volume inference via small specialized models. If a scenario names none of these, the correct answer is a catalog model with grounding and instructions.

DimensionStandard Copilot / catalog modelCustom Foundry model
Domain specificityLowHigh
Compliance demandsModerateHigh
Performance demandsModerateHigh
Data confidentialityModerateFull data control
Solution complexityLow–mediumHigh
Inference-cost optimizationBaselineHigh — small specialized models at volume

The design steps, in order: business objectives (accuracy, time, cost targets) → data assessment (gaps in labeling, quality, diversity; governance permission to train on the data) → select the path (fine-tune a foundation model | train a domain SLM | hybrid with prebuilt copilots) → enterprise integration (D365, Azure Functions/Logic Apps, Foundry agent workflows, AI Search, automation pipelines) → validate and evaluate (scenario evals, safety/bias, stress/latency/scale, ROI).

Operationalization is what makes this the bottom rung. A custom model means you own: monitoring and observability (drift, degradation, friction, latency, unexpected outputs); versioning and lifecycle (version trails, update pipelines, rollback); and deployment automation through MLOps/GenAIOps (validations, approvals, environment-specific deploys). The exam framing: prompt engineering and retrieval tuning come first; a custom model is what you build when those demonstrably can't hit the accuracy bar and one of the five justifications applies.

Agents in Microsoft 365 Copilot

A declarative agent is an M365 Copilot agent defined by instructions + knowledge + actions, running on Copilot's orchestrator and inheriting its guardrails. More generally, a Copilot agent is a modular, instruction-driven AI component scoped to a specific task or workflow: task automation, information retrieval (Graph plus integrated systems), multi-step operations (classification, analysis, routing), and collaboration (drafts, summaries). Agents operate in Teams, Outlook, Loop, and SharePoint, and in custom line-of-business apps via extensibility points. [source, source]

The three-step design framework

A. Understand the core problem — the task, the goal, the decisions involved, the systems touched. B. Define the behavior — the agent's role, its allowed and disallowed capabilities, guardrails, and escalation conditions. C. Connect data and tools — Graph, SharePoint/OneDrive/Teams, connectors and actions, custom APIs — always least-privilege, zero-trust. Notice the shape: problem before behavior, behavior before wiring. A scenario that jumps straight to connectors has skipped the two steps the exam rewards.

Collaborative patterns for multiple agents

PatternShapeUse when
SequentialAgent A → Agent B → user reviewPipeline work that needs a human checkpoint
Parallel evaluationAgents score independently; results are combinedYou want independent judgments merged into one answer
Feedback loopIterate until the output meets the barDrafts that improve over successive passes
Orchestrated interactionA primary agent delegates by intent or conditionsRouting work across specialties

Whichever pattern you choose: clear handoff rules and responsibility boundaries are the design deliverable. An orchestrated agent without explicit delegation conditions is a router with no route table.

Agent Builder — the easiest declarative path

Agent Builder is the guided authoring surface inside Microsoft 365 Copilot: step-by-step configuration, built-in tools, declarative instructions, a testing workspace, and publishing controls. The workflow is worth memorizing as a sequence: purpose → instructions, tasks, and guardrails → data sources → actions and permissions → test → publish to targeted users/groups. After publishing, operations are: monitor quality and feedback; update instructions; manage access control; review logs; version the agent; and identify new scenarios. When a scenario describes a business user — not a developer — building an M365 Copilot agent, Agent Builder is the answer. [source]

The four extensibility layers of Copilot Studio

Copilot Studio's boundary doesn't break all at once — it stretches through four layers, in increasing order of power and cost. The exam's pattern is "which layer solves X," so learn each layer as what it can change, what it can't, and one concrete example. [source]

LayerWhat it can changeWhat it can'tConcrete example
1. Instruction-levelPurpose, role/constraints, action patterns, escalation rules — prompt modification without a rebuildAdd new tools, skills, or data connections — it changes behavior, not capabilityRewrite escalation rules so billing disputes over $10,000 always route to a human
2. Skill/capabilityRetrieval skills (enterprise content), action skills (connectors/custom APIs), multi-step workflows, domain knowledge — modular and reusableReach a system no connector or API can see — skills sit on top of available actionsAdd a reusable refund-lookup action skill backed by a custom API
3. IntegrationD365/M365/custom database/LOB retrieval; Power Automate actions; external APIs; published events and commandsChange the agent's logic itself — it wires systems to the agent, not the reverseConnect the agent to F&O vendor records and a Power Automate approval flow
4. Pro-code (VS Code)Custom agent logic and components, code-based tools/actions, custom transformations and orchestration, source control integrationStay in the low-code loop — you now own code, with source control and a dev lifecycleBuild a custom orchestration component in VS Code, checked into source control

Integration-layer design carries its own checklist: governance, least-privilege, standardized commands, and consistent entity mapping across systems. Three architecture patterns sit above the layers: modular agent architecture (interchangeable components), multi-agent collaboration (research, workflow, and communication agents talking over defined protocols), and domain-context design (terminology, rules, access policies, and outcomes per domain).

The three architecture principles that govern all of this: fit for purpose, operability, and trust/traceability/transparency. They complement — not replace — the Azure Well-Architected Framework, the Power Platform Well-Architected Framework, and NIST. A distractor that says an agent architecture framework substitutes for WAF is wrong on its face. [source, source, source]

MCP: a standardized contract for business context

The Model Context Protocol (MCP) is a standardized contract for what context an agent can access and how to interpret it. The analogy that ties this lesson to lesson 6: MCP is to context what the custom connector's OpenAPI definition is to actions — the shared description both sides build against. In Dynamics 365 Finance & Operations, MCP exposes the business semantics themselves: entities, relationships, labels, metadata, and domain objects — customers, vendors, products; workflows, statuses, and approval chains; financial dimensions and ledger models; localization rules. [source]

Why it matters: consistent business semantics across every agent that consumes the contract; grounding in real F&O context, which reduces misinformation; interoperability across multiple apps; explainability and governance; and faster extensibility, because each new agent inherits the semantics instead of relearning them.

Instruction design for an MCP-consuming agent has five named parts: a purpose statement, a role definition, behavior rules, context consumption logic (how the agent uses the MCP data it's given), and action boundaries.

The three integration patterns

PatternWhat the agent doesNamed examples
A. Context-driven reasoningReasons over live business semantics to answer and judgeCompliance, finance, procurement
B. Workflow-integrated agentsEmbedded inside the business process itselfApprovals, exception escalation, status summaries
C. Multi-agent collaboration via shared MCP contextSeveral agents interoperate over the same semanticsHR + Finance + Supply Chain agents

Governance: least-privilege by user identity; MCP context boundaries aligned to compliance domains; decision logging; instructions that enforce Responsible AI; and AI CoE ownership. The boundary idea is the one to internalize: the contract defines what each agent may see, and you align those boundaries to the same compliance domains your data governance already uses.

Computer Use: the last-resort UI bridge

Computer Use lets an agent operate a user interface directly: control the mouse and keyboard, navigate websites and desktop apps, read onscreen text and UI elements, run multi-step tasks, and execute across applications. The runtime flow: request → analyze the UI (vision + reasoning) → build a step plan → act via the Computer Use channel → validate and report. [source]

The golden rule: use Computer Use only when APIs are unavailable. It is the bridge of last resort, not a convenience — an exam option that reaches for Computer Use while an API or connector exists is the trap.

Suitable — reach for Computer UseNot suitable — do something else
No API/connector exists: legacy systems, vendor portals, desktop-only appsAn API or connector exists — build the connector instead (the golden rule)
Repetitive UI-driven tasks: data entry, form submission, copy/pasteEntering sensitive data — avoid by design
Multi-app navigation: portal → CRM, downloading reportsUnmonitored production use — UI changes break it; you need monitoring and a fallback plan
Dynamic pages that need human-like reasoning

Design for variability, because UIs are not contracts: give clear goal-oriented tasks broken into steps; set context and constraints (allowed apps and sites, data boundaries, prohibited actions, time and retry limits); write descriptive instructions — "click the blue Submit button," not coordinates; validate after each step; and fail with graceful errors. Configuration: enable Computer Use in agent settings; configure permissions and allowed apps; add Computer Use actions (click, type, scroll, extract, navigate); pick the reasoning mode (lesson 5's standard/deep choice applies here); and watch/debug runs in the test canvas. Governance: least-privilege application access; avoid sensitive data entry; transparency; action logging; and — because UI-change fragility is inherent — monitoring plus a fallback plan.

Agents for Teams and SharePoint

Copilot Studio-built agents publish into the two M365 surfaces where work actually happens. In Teams: chat and channel answers, message-triggered workflows, and contextual answers over M365 data. In SharePoint: retrieval over site, list, and library content; site-specific Q&A; and content-management help. Grounding in both respects user permissions via Microsoft Graph (files, lists, pages) — lesson 2's permission trimming applies unchanged: a user without access simply never grounds on that content, and you test as personas. [source]

SharePoint agents draw knowledge from site pages, document libraries, lists, news, policies, and wikis — and site context is automatic: the agent knows which site it belongs to, treats that site as its primary grounding, and adapts to the site's structure. They also assist the site owner: drafting pages, managing metadata, accessibility, and organization. Teams agents add conversational automation, multi-user collaboration in group conversations with shared knowledge, and task automation — "create a task for this message," "summarize the last 10 messages."

Optimization guidance

  • Grounding strategy: SharePoint as the primary source, Graph for cross-tenant reach, well-structured and tagged content.
  • Permissions: inherit user permissions; app registration plus consent.
  • Prompt/behavior design: concise answers, clarifying questions, use of metadata.
  • Governance/lifecycle: version control, usage monitoring, periodic grounding review, AI CoE alignment.

The four named patterns

PatternWhat it does
SharePoint knowledge assistantSite-scoped Q&A over pages, libraries, and lists
Teams project assistantChannel answers plus message-triggered task automation
Org policy assistantOrganization-wide policy answers from governed sources
Site owner support agentHelps owners draft pages, manage metadata, and organize the site

Check yourself

1. A marketing team wants an assistant inside Teams and Outlook that summarizes campaign documents from SharePoint, drafts briefs, and handles similar simple tasks — all data lives in Microsoft 365. Best approach?

Interaction in M365 apps, M365 data, simple actions, no orchestration needs, built-in governance wanted — every row of the comparison matrix lands on "extend." Copilot Studio and Foundry buy autonomy and custom logic the scenario never uses, and a custom model answers a question nobody asked.

2. An existing service agent works well, but leadership wants escalation rules rewritten so billing disputes over $10,000 always route to a human — no new tools, data, or systems. Which extensibility layer?

Purpose, role/constraints, action patterns, and escalation rules are exactly the instruction-level layer's remit — prompt modification without a rebuild. A new skill adds capability nobody requested; integration wires external systems; pro-code rewrites logic. Each overshoots a rules-only change.

3. That same agent must now read vendor records from Dynamics 365 F&O and start a Power Automate approval flow. Which extensibility layer?

D365/M365/LOB retrieval, Power Automate actions, and external APIs are the integration layer's stated remit — with governance, least-privilege, standardized commands, and consistent entity mapping as its design checklist. Instructions can't conjure a connection, and pro-code is premature while connectors and flows suffice.

4. A utility runs 40 million meter-reading classifications daily. The vocabulary is highly domain-specific, retrieval-tuned catalog models still miss the accuracy bar, and a small specialized model would slash inference cost. Is a custom model justified?

Domain-specific language, insufficient off-the-shelf accuracy after tuning, and high-volume inference-cost optimization via a small specialized model are three of the five stated justifications — this scenario clears the bar. Option d confuses hosting topology with the build decision; GPUs and containers are a separate rung with separate triggers.

5. HR wants an agent answering policy questions in the company's tone. The content is general HR language, and grounding over the policy SharePoint site already returns accurate answers. Right call?

General-purpose Q&A with adequate accuracy is the catalog model's stated profile, and tone is an instruction-layer problem, not a training problem. Building a custom model when grounding over a general model already suffices is the classic anti-pattern — you'd inherit evals, drift monitoring, and rollback for nothing.

6. An F&O agent must run inside the purchase-approval workflow: reading approval chains and financial dimensions, escalating exceptions, and posting status summaries. Which MCP integration pattern?

Approvals, exception escalation, and status summaries are the workflow-integrated pattern's named examples. Context-driven reasoning fits analysis and judgment calls; multi-agent collaboration fits several agents sharing context across domains. Option d is a Copilot Studio extensibility layer, not an MCP pattern at all.

7. Every morning, ops staff copy invoice data from a vendor's web portal into the ERP. The portal has no API and no connector. Best approach?

"No API/connector" plus "repetitive UI-driven task" plus "vendor portal" hits all three Computer Use suitability conditions. Option a is the trap — it requires the very API the stem says doesn't exist; the golden rule only licenses Computer Use because that API is missing. The ERP connector reaches the destination but never touches the portal.

8. A project team wants an agent in its Teams channel that answers from the project's SharePoint site, summarizes the last 10 messages, and creates tasks from messages. Which pattern?

Channel answers plus message-triggered automation — "summarize the last 10 messages," "create a task for this message" — is the Teams project assistant pattern. The SharePoint knowledge assistant is site-scoped Q&A; the site owner agent drafts and organizes pages; the policy assistant serves org-wide policy content. The surface and trigger decide the pattern.

9. A business user with no developer background wants to create a declarative Microsoft 365 Copilot agent through guided configuration and publish it to her team. Easiest path?

Agent Builder is the easiest declarative path: guided step-by-step configuration, built-in tools, a testing workspace, and publishing to targeted users/groups — purpose → instructions → data sources → actions → test → publish. The other three options each assume maker or developer skills the author profile explicitly rules out.

Apply it: three extensibility designs

Decide each before opening the reveal.

A. Northwind Logistics coordinators spend about 90 minutes every morning copying shipment statuses from three carrier systems into Dataverse. Two are web portals with no API and no connector; the third is a desktop-only client. The clicks are identical every day. Design the agent — including what happens when a carrier redesigns its portal.

Your design?

Golden-rule gate first: confirm no API or connector exists — given. That licenses Computer Use. Task design: one clear goal-oriented task per carrier, broken into steps; descriptive instructions ("click the blue Track button," never coordinates); validate after each step; graceful errors. Constraints: an allowed-apps/sites list, data boundaries, prohibited actions, and time/retry limits. Configuration: enable Computer Use in agent settings, configure permissions and allowed apps, add Computer Use actions (click, type, scroll, extract, navigate), choose the reasoning mode, and watch/debug in the test canvas. Governance: least-privilege application access (an account with only the portal rights the task needs), no sensitive data entry, transparency, and action logging. The redesign answer is the governance one: UI-change fragility is inherent, so you ship monitoring plus a fallback plan — when the portal layout changes, the agent fails safe to a human queue rather than pasting garbage into Dataverse. [source]

B. Contoso Manufacturing runs Dynamics 365 F&O. Compliance, HR, and Finance each want agents, and all three must interpret "approval chain," "financial dimension," and vendor status identically. Auditors require logged, explainable decisions. Design the approach.

Your design?

Contract: MCP in F&O exposes the business entities, relationships, labels, metadata, and domain objects — customers, vendors, products, approval chains, financial dimensions, ledger models — so all three agents reason over one shared set of business semantics: consistency across agents, grounding in real F&O context (less misinformation), interoperability, and the explainability the auditors demanded. Patterns: context-driven reasoning for the compliance officer's judgment calls; workflow-integrated agents for approvals, exception escalation, and status summaries; multi-agent collaboration via shared MCP context when questions span HR + Finance + Supply Chain. Instructions per agent: purpose statement, role definition, behavior rules, context consumption logic (how MCP data is used), action boundaries. Governance: least-privilege by user identity; MCP context boundaries aligned to the compliance domains; decision logging; RAI-enforcing instructions; AI CoE ownership. [source]

C. Fabrikam's legal department wants an assistant that answers from its SharePoint site — pages, document libraries, lists, and policy wikis. Two libraries are restricted to department members and answers must never leak them. The site owner also wants help drafting and organizing new pages. Design the agent and its optimization plan.

Your design?

Agent: a SharePoint agent built in Copilot Studio — this combines the SharePoint knowledge assistant and site owner support agent patterns. Site context is automatic: the agent knows its site, treats it as primary grounding, and adapts to the site's structure; site-owner assistance covers drafting pages, metadata, accessibility, and organization. The restricted-library requirement is not a feature to build — it's permission trimming: grounding respects user permissions via Graph, so restricted content simply doesn't exist for outsiders. Verify by testing as personas, never as the site owner (lesson 2's availability rule). Optimization: grounding strategy — SharePoint primary, well-structured and tagged content; permissions — inherit user permissions, app registration plus consent; prompt design — concise answers, clarifying questions, metadata use; lifecycle — version control, usage monitoring, periodic grounding review, and AI CoE alignment. [source]
