The agent operating model

Design overall AI strategy — CAF phases, business roles, the AI CoE, and multi-agent design

1. (Lesson 1) A VP proposes jumping straight to a custom Foundry build "for maximum flexibility." What does the SaaS-first principle say — and what burden does a custom build inherit?

Reveal

Always open by asking whether a prebuilt SaaS agent meets the functional requirements; if yes, stop. Custom builds carry governance, evaluation, and ops burden you must justify — control is paid for with ownership.

2. (Lesson 2) Name the five grounding dimensions, and say which one fails silently.

Reveal

Accuracy, relevance, timeliness, cleanliness, availability. Availability fails silently — retrieval is permission-trimmed per user, so the agent answers from a poorer evidence base and nobody gets an error.

3. (Connect them) If availability failures are silent, can the data-availability check wait until the agent is in production? Which phase must own it?

Reveal

No — a silent failure never pages anyone; operations telemetry sees a "working" agent. Data availability must be verified before build, as one of the agent readiness criteria in the CAF Plan phase. That's the map this lesson teaches.

The map: CAF phases ↔ the agent lifecycle

The Cloud Adoption Framework's AI adoption process runs six phases — Strategy, Plan, Ready, Govern, Secure, Manage. The agent lifecycle runs four stages — Plan agents, Govern & secure agents, Build agents, Operate agents. They interlock, and the interlocking is the exam content. The AI Center of Excellence

The AI CoE is the organizational structure that makes the roles and the CAF map durable. Three elements are non-negotiable: executive sponsorship, a dedicated CoE leader, and a multidisciplinary team — strategy, data, ML, governance, security, ops, and business SMEs. [source]

Placement and maturity

Within Data / Enterprise ArchitectureA strong data or EA org already exists to host it

Centralized is a starting stage, not a destination — the arc exists because gatekeeping doesn't scale. The exam likes "the CoE should remain the permanent approval authority for all agents" as a wrong answer.

Single agent or many — the triggers, deepened

Lesson 1 gave you the rule: single agent first, multi-agent only on explicit triggers. Here is the full trigger set, with why a single agent fails in each case — that mechanism is what separates trigger from taste: [source, Microsoft AI Decision Framework]

TriggerWhy one agent strugglesWhat multi-agent buys
Crossing security/compliance boundariesOne agent's permissions span what policy says must stay separatedScoped permissions per agent; the boundary holds
Multiple teams own distinct knowledge, data, release cyclesOne backlog and one deployment can't serve two cadencesEach team owns, versions, and releases its own agent
Roadmap spans 3–5+ functionsInstructions grow incoherent; evaluations blur across functionsModular specialization — single clear responsibility per agent
Dependent action series across 2+ workstreamsOne prompt must hold the entire choreographyOrchestrated handoffs with explicit contracts

Before paying for many agents, exhaust the cheap fixes: persona switching, better retrieval, policy controls, a larger context window. Mediocre retrieval is a grounding problem (lesson 2), not an agent-count problem. And when you do go multi-agent, the platforms divide the labor: M365 Copilot hosts domain agents for immediate value, Copilot Studio hosts business-led task/retrieval agents, and Foundry hosts connected agents with complex orchestration. [source]

Orchestration patterns (Microsoft Agent Framework)

Five named patterns. Learn each as what it is → when to choose it: [source]

PatternWhat it isChoose when
SequentialDeterministic pipeline; each agent's output feeds the nextFixed stages, order matters, auditability wanted
ConcurrentParallel subtasks whose results are aggregatedIndependent subtasks; breadth or latency wins
Group chatModerated discussion; agents propose, a moderator selectsDeliberation- or proposal-style problems
HandoffControl transfers to a specialist agent or human when a threshold tripsEscalation on confidence, risk, or policy gates
MagenticDynamic specialization; an orchestrator pulls in expert agents at runtimeThe expert set isn't known until runtime

The reliability rule. Treat orchestration as a workflow — with state, branching, and error handling — not as a conversation. Avoid prompt-to-prompt daisy chains: if agent A's prose feeds agent B's prompt with no contract in between, you have a demo, not a system. [source]

Connected agents: the design checklist

  1. Define the main agent — mission, guardrails, metrics, tooling. It routes to specialists in natural language.
  2. Identify connected agents by role — Planner, Researcher, Reviewer, Actuator — each with a minimal instruction set and scoped permissions.
  3. Model the collaboration — contracts and state handoffs: pass IDs, not raw content. The receiving agent resolves the reference itself, which keeps payloads small, permissions scoped, and audit trails clean.
  4. Prototype, then iterate — and prune redundant agents as the design stabilizes.

Evaluation checkpoints for any connected-agent design: one clear responsibility per agent; security scopes per agent; graceful degradation when a specialist fails; observability hooks at every handoff. [source]

The prompt library: one governed artifact

A prompt library is the CoE's reusable-prompt asset — curated and governed for consistency, governance, efficiency, quality, and scalability. Keep it in perspective: it's one artifact type the CoE's skilling/standards function owns, not a program of its own. [source]

Quality bar — the four pillars: Clarity, Context, Constraints, Output format. Governance metadata per prompt: purpose, owner, version, last-updated, applicable systems, risk classification, grounding sources. Storage options: SharePoint, GitHub Enterprise, Azure DevOps, or Copilot Studio prompt guides. Lifecycle: version control; review and approval by domain experts, RAI reviewers, and security; testing across inputs, edge cases, and model versions; retire outdated prompts and monitor drift. [source]

The maturity model runs L1 basic → L2 guided → L3 structured → L4 optimized (few-shot, formatting) → L5 enterprise (templates, version control, governed library). The exam phrase to recognize is "enterprise governed prompt library" — that's L5, and it's a CoE function, not a team-folder habit. [source]

Check yourself

1. A program lead is writing the entry gate every agent proposal must pass before build begins: data availability, governance readiness, identity model, connectors. Which CAF phase produces this artifact?

Agent readiness criteria are an output of AI Plan, alongside the skills assessment and proof of concept. Strategy produces the brief and technology plan; Ready builds the landing zone and governance charter; Govern enforces. Readiness is the gate checked during planning — before foundations exist.

2. Where is the agent governance charter — capability access, data boundaries, approvals, monitoring — first established?

Ready lays the foundation: landing zones, the data access model, and the charter itself. Govern + Secure then enforce it — Azure Policy, risk register, audit trails, escalation. The exam splits foundation (Ready) from enforcement (Govern/Secure) precisely because the names blur.

3. A funded, sponsored, well-governed agent launches on schedule. Six months later adoption is near zero: users were never trained and drifted back to old habits. Which missing role best explains it?

Sponsorship and governance were present; what failed is enablement. The change management & skilling lead owns training and adoption — without one, working technology dies of disuse. Match the symptom to the failure-mode column, not to the most senior-sounding role.

4. A claims process must run intake → coverage check → payout in strict order, each stage a specialist agent, fully deterministic, no parallelism wanted. Which orchestration pattern?

Fixed stages in a fixed order with deterministic control flow is the sequential pattern — a pipeline where each agent's output feeds the next. Concurrent runs independent subtasks in parallel; group chat deliberates; Magentic picks experts dynamically at runtime.

5. A support agent must yield control — to a specialist agent or a human — whenever its confidence drops or a risk threshold trips. Which pattern fits?

Handoff exists for exactly this: transfer to a specialist or human when a threshold — confidence, risk, policy — is crossed. Sequential and concurrent keep the same agents in the same roles throughout; group chat deliberates rather than escalates.

6. The AI CoE must personally approve and build every agent. Nine months in, its queue is forty projects deep, and two business units have started building agents in secret. Name the failure mode.

A centralized gatekeeper approving everything collapses into a bottleneck — and the secret building is the symptom (shadow AI), not the disease. The maturity arc exists to escape this: evolve centralized → hybrid → advisory, with governance embedded in platforms rather than in a queue.

7. A team wants to split one HR policy Q&A agent into four agents — one per policy domain — because retrieval quality is mediocre. One SharePoint estate, one team, one release cycle. Your advice?

No trigger is present: no boundary crossed, one owning team, one release cycle, a single function. Mediocre retrieval is a grounding problem — scope knowledge sources and clean the content — and persona switching covers per-audience tone. Multi-agent would multiply cost and governance without fixing retrieval.

8. Which situation most clearly justifies a multi-agent design?

A roadmap spanning 3–5+ functions plus multiple owning teams with distinct release cycles are explicit triggers. Languages, connector counts, and long instructions are single-agent problems — solved with retrieval, persona switching, or tighter instructions, not orchestration.

9. Leadership asks where SLOs, retraining rules, and deprecation criteria for production agents are documented. You point to:

Operate-stage artifacts live in Manage: telemetry, SLOs, rollout patterns, behavior monitoring, and the Agent Ops playbook with retraining and deprecation rules. The charter governs access and boundaries; the technology plan picks platforms; readiness criteria gate the build.

Apply it: three operating-model problems

Decide each before opening the reveal.

A. Contoso (12,000 employees, financial services) is standing up an AI CoE. The CIO will personally sponsor it and proposes a standalone three-person team that must approve every agent use case before any work begins. Critique the design.

Your call?

Two elements right, the rest is a failure-mode checklist. Executive sponsorship and a dedicated leader are present — good. But three generalists are not the multidisciplinary team (strategy, data, ML, governance, security, ops, business SMEs). Standalone placement is the last resort, only if no supporting team exists — check for a CCoE or Data/EA home first. And "approves everything" is the centralized gatekeeper posture: acceptable as a starting maturity stage only with an explicit path toward hybrid, then advisory — otherwise it becomes the bottleneck that breeds shadow AI. Finally, assign the six functions — strategy, skilling, governance/standards, intake/prioritization, delivery support, operations — not just approval power. [source]

B. Fabrikam's returns flow: an intake step validates claims, a warranty step checks coverage, a fraud step scores risk, a resolution step issues refunds. Customer Service owns intake and resolution; the Warranty and Fraud teams own their steps and ship on their own cadence. The lead developer proposes one agent with "a really good prompt." Settle the debate — and if multi-agent, which pattern(s)?

Your call?

Multi-agent, justified twice over: multiple owning teams with distinct release cycles, and a dependent action series across workstreams — with fraud scoring likely behind a compliance boundary besides. One prompt would force a single team to own everyone's logic and hold everyone's permissions. Patterns: Sequential for the deterministic intake → warranty → resolution pipeline, plus Handoff to a human when the fraud score crosses threshold. Contracts: pass claim IDs between agents, not raw content; scope each agent's permissions to its domain; run the whole thing as a workflow with state, branching, and error handling — no prompt-to-prompt daisy chains. [source]

C. Northwind's CoE finds two hundred copy-pasted prompts circulating in a Teams channel — some embed customer data, several still enforce last year's policy. An engineer proposes "dropping them all in a shared SharePoint folder." Is that a prompt library?

Your call?

That's storage, not a library. A governed library needs the metadata (purpose, owner, version, last-updated, applicable systems, risk classification, grounding sources), a review/approval workflow (domain experts, RAI, security), testing across inputs and model versions, and lifecycle rules — retire the outdated, monitor drift — plus the four-pillar quality bar: clarity, context, constraints, output format. The customer-data prompts need remediation, not a folder. Done right, this is the jump from L1 ad-hoc to L5 enterprise governed library, owned by the CoE's skilling/standards function. [source]
