The five grounding dimensions

Grounding means the agent responds using trusted, domain-specific organizational data rather than the model's parametric memory. Every AB-100 "the agent gave a bad answer" scenario is, at root, one of five dimensions failing. Learn each as a triple: definition → failure mode → how an architect detects and fixes it. [source, source]

DimensionDefinitionFailure modeArchitect's detect & fix
AccuracyContent is correct, verified by SMEs and authoritative sourcesConfident misinformation — the model fills gaps from parametric memorySME spot-checks; evaluate content before upload; store authoritative content in SharePoint/OneDrive so there is one source to trust
RelevanceRetrieved content matches the task and the user's intentConceptually-similar-but-wrong retrieval — right topic, wrong product/region/versionRun the agent's real questions and inspect what comes back; scope knowledge sources; strip off-topic near-neighbors
TimelinessContent is current; the semantic index continuously updates; refresh schedules are setAnswers cite superseded versions that still circulate in the estateAsk date-sensitive questions; check last-modified on whatever got cited; archive superseded docs; set refresh schedules
CleanlinessContent is structured, de-duplicated, with minimal noise metadataData pollution — dupes and noise degrade embeddings and retrieval precisionDuplicate audits; consistent formatting templates; strip junk metadata before content enters the pipeline
AvailabilityContent is accessible and indexable — for the user who is askingSilent omission: the agent answers without the best content and nobody gets an errorTest retrieval as each user persona (trimming is per-user); review permissions; keep content where the index can reach it

Two exam instincts to build here. First, availability failures are silent — the agent doesn't error, it just answers from a poorer evidence base, so "it works on my account" proves nothing. Second, the dimensions are a pre-flight checklist, not a postmortem: evaluate content before upload, keep authoritative content in SharePoint/OneDrive, enforce consistent formatting, review permissions, collaborate with SMEs — all before the first user prompt. [source]

How M365 grounding actually works

Copilot and Copilot Studio ground over your tenant using two mechanisms — one built ahead of time, one exercised at query time. The split matters. [source, source]

Ahead of query time — the semantic index. Organizational content in Microsoft Graph is semantically indexed: a lexical + semantic map across Graph content that is continuously updated and honors permissions. This is why a Copilot answer can reflect a document edited recently without anyone "retraining" anything.

At query time — the Copilot Retrieval API. When a grounded answer is needed, the Retrieval API pulls relevant passages from SharePoint, OneDrive, and connector sources — and it does so as the calling user. The API never returns content beyond that user's access. Results are permission-trimmed at query time, not at index time.

Three architectural consequences:

  1. Grounding is per-user. The same agent, same question, two users → potentially two different evidence sets and two different answers. This is a feature (security), but it breaks naive testing.
  2. Over-permissioned content is a grounding bug. If an intern gets an answer citing a confidential document, the defect is in SharePoint permissions — not in the prompt, the agent, or the model. The fix lives at the permission layer because trimming happens there.
  3. You test retrieval as personas, not as admin. An admin account sees everything; a new hire's account may see nothing. Persona-based retrieval tests are how you detect the silent-omission failure mode from the availability dimension.

The RAG pipeline, stage by stage

For custom groundings (Foundry agents, Azure AI Search-backed knowledge), the retrieval-augmented generation pipeline is the canonical flow. You must be able to reproduce this from memory: [source, source]

  1. Ingestion — pull raw content from source systems into the pipeline.
  2. Streaming — keep content flowing incrementally so the index tracks source changes without full re-runs.
  3. Cleaning — strip boilerplate, duplicates, and junk metadata. This is where the cleanliness dimension is won or lost.
  4. Chunking — split documents into passages sized for retrieval.
  5. Embedding — convert each chunk into a vector. Done once, ahead of query time.
  6. Indexing — load vectors and text into the search index.
  7. Retrieval — given a user turn, fetch the top-K candidate passages. Default-preferred mode is hybrid: vector + keyword + semantic ranker.
  8. Prompt assembly — compose instructions + retrieved passages + the user question into the model call.
  9. Orchestration — the agent's control flow: when to retrieve, rewrite a query and retry, call a tool, or abstain.
  10. Monitoring — track retrieval quality and grounding failures; feed findings back into earlier stages.

Why externalize to an index instead of querying live systems per turn? Follow the arrows: embedding (5) and indexing (6) happen before anyone asks anything. Retrieval quality depends on that precomputed work — you cannot embed the corpus at query time. And per-turn live queries would pile unpredictable read load onto transactional systems. So grounding runs against an externalized index that stays fresh through streaming ingestion. RAG's stated advantages — real-time data access, privacy preservation, misinformation mitigation — all follow from this arrangement: fresh indexed content (not a stale model), data stays in your boundary (not sent for training), and trusted content constrains the answer. [source]

Why hybrid beats pure vector. Vector similarity is excellent at intent ("how do I return a damaged order") and notoriously soft on exact tokens — part numbers, error codes, proper nouns blur into their nearest neighbors. Keyword retrieval nails exact tokens but misses paraphrase. Hybrid runs both and lets the semantic ranker re-score the merged candidates by relevance. That is why hybrid (vector + keyword + semantic ranker) is the default-preferred retrieval mode, and why "our vector search misses part numbers" is a retrieval-mode bug, not an embedding-model bug.

Organizing data for AI readiness

The Cloud Adoption Framework's data architecture for AI agents reduces to six moves. Do them in roughly this order, and do governance earlier than feels necessary: [source]

  1. Centralize knowledge sources. Authoritative content lives in known homes: SharePoint, OneDrive, Dataverse, Azure Storage. Scattered copies are future data pollution.
  2. Normalize and structure. Consistent formats and clean metadata, so embeddings and retrieval aren't fighting noise.
  3. Build semantic indexing. Make content retrievable by meaning, not by folder path.
  4. Provide multiple access paths. APIs, search indexes, RAG pipelines, Graph connectors, SQL endpoints — and choose per consumer. Stable documents belong in an index; volatile per-record facts belong behind an API or connector the agent calls at runtime.
  5. Governance early. Purview access policies, sensitivity labels, lineage, and quality rules — applied to the data before ingestion, not retrofitted after a security review finds the agent reading labeled content it shouldn't.
  6. Keep it authoritative and updated. One source of truth per domain, with refresh discipline — the timeliness dimension, operationalized.

Check yourself

1. A benefits agent keeps citing the 2024 expense policy even though the 2025 version was published to the same SharePoint library months ago. Both documents are retrievable. Which grounding dimension should you fix first?

Both versions are indexed and retrievable, so availability is fine — and each document was accurate when written. The defect is freshness discipline: a superseded version still circulates. Archive or demote the old document and set refresh schedules so current content wins retrieval.

2. Two sales reps ask the same agent for the enterprise discount policy. One gets a precise, cited answer; the other is told no such policy exists. The document sits in one indexed SharePoint library. Most likely cause?

Retrieval is permission-trimmed per user at query time — the Retrieval API never returns content the caller can't access. Same agent, same index, different user means check permissions, not the pipeline. The failure is silent by design, which is why you test retrieval as personas.

3. A proposal agent drafts answers that blend fragments of three near-identical copies of the same case study, saved by different teams in different libraries. Which grounding dimension is failing?

Duplicate content is data pollution — the cleanliness dimension. Duplicates split retrieval scores and degrade embedding precision, so the model receives three partial copies instead of one authoritative passage. Dedupe to a single authoritative copy before tuning anything else.

4. A customer-facing shopping agent needs product lookups at very low latency across regions, with vector similarity over embeddings stored next to the product documents. Which operational database fits?

Cosmos DB is the low-latency operational store with native vector search — embeddings colocated with the documents it serves. Azure SQL and PostgreSQL are strong relational fits, and Fabric is the analytical layer, not an operational store you point a live customer agent at.

5. Testing shows the agent answers even when retrieval returns nothing useful. You want it to rewrite the query, retry once, then abstain. Which RAG pipeline stage owns that change?

Flow control — deciding when to retrieve, rewrite and retry, or abstain — is orchestration. Retrieval fetches candidates; orchestration decides what to do with the result. Monitoring would only tell you it happened; ingestion can't help at query time.

6. Field engineers search by exact part numbers like "XJ-4402" and the vector-only index keeps missing them, returning conceptually similar parts instead. Best fix?

Exact tokens are keyword's strength; vector similarity blurs identifiers into neighbors, and a bigger embedding model won't change that. Hybrid with the semantic ranker is the default-preferred retrieval mode — it keeps semantic recall and restores exact-match precision.

7. In a design review, an engineer proposes skipping the search index and having the agent query the ERP's live database on every turn instead. Strongest architectural objection?

The embedding and indexing stages run before query time — that precomputed work is exactly why grounding hits an externalized index. Per-turn live queries can't reuse it and pile read load onto a transactional system. The other options are simply false: operational databases do store vectors, authorized queries are legitimate, and the ranker runs in Azure AI Search.

8. A month before launch, security review finds the agent retrieving documents whose sensitivity labels prohibit that use. The labels existed all along. Where was the cheapest point to catch this?

Governance early: Purview access policies, sensitivity labels, and lineage belong in the data-organization phase — before content is ingested and indexed. Prompt instructions and runtime filters are retrofits that cost more, leak more, and put the fix in the wrong layer.

Apply it: Northwind Traders, three data problems

Northwind Traders (retail, 8,000 employees, M365 + Azure estate) brings you three grounding problems. Decide each before opening the reveal.

A. Their support agent is grounded on a SharePoint knowledge library. Senior techs report excellent answers; new hires report thin, generic ones. This week, an intern received an answer quoting a confidential field-engineering bulletin. Two symptoms — one root cause area?

Your call?

Yes: permissions. Retrieval is trimmed per user at query time, so new hires silently omit content their roles can't reach (availability failure), and the intern saw content they shouldn't reach (over-permissioned source). Neither fix lives in the prompt: correct the SharePoint permission model, apply sensitivity labels, then re-test retrieval as each persona. [source]

B. Northwind's order system runs on Cosmos DB across regions; ten years of sales history sits in an aging SQL Server warehouse; the board wants the estate "AI-ready." Place the pieces.

Your call?

Layer it, don't consolidate blindly. Keep Cosmos DB as the operational store — low latency with native vector search covers product-similarity features in the shopping app. Land the sales history in Microsoft Fabric as the analytical store for unified reporting. Put Azure AI Search in the intelligence layer, indexing the curated product and policy content agents will retrieve. Agents (Copilot Studio or Foundry) consume the intelligence layer and sanctioned APIs — never the transactional store directly. [source, source]

C. The agent roadmap has two flagship questions: "how do I assemble product Y?" and "what's the current status of order X?" Same retrieval design for both?

Your call?

No — match the access path to data volatility. Assembly instructions are stable documents: index them and serve via RAG (that's the pipeline's job). Order status is a volatile, per-record fact: by the time an index refresh lands, it's stale, so expose it through an API or connector action the agent calls at runtime. CAF's "multiple access paths" guidance exists precisely for this split — APIs, search indexes, RAG, Graph connectors, SQL endpoints are complements, not competitors. [source]
